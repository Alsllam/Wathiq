# 6.6 — Auth: OIDC code+PKCE

> **Phase:** 6 · **App:** mobile · **Commit:** `step(6.6): add OIDC sign-in with secure token storage and a refresh-retrying Dio interceptor` · **Date:** 2026-09-07

## What was built

The auth stack, walled the way this project walls everything: an `Authorizer` interface (sign
in / refresh) whose real implementation wraps `flutter_appauth` — one call runs the whole
code+PKCE dance 4.4 wired by hand, against the same OpenIddict issuer, `Wathiq_App` client,
**trailing slash and all** — and a `TokenStore` interface whose real implementation is
`flutter_secure_storage` (Keychain / EncryptedSharedPreferences). `AuthNotifier`
(`AsyncNotifier`, hydrating from storage on launch) exposes sealed `SignedOut`/`SignedIn`
states; the AppBar switches on them exhaustively. Dio gained the `authInterceptor` idiom:
bearer on every request, and on 401 **one flagged retry** through
`refreshAccessToken()` — token rotation persisted, a dead refresh token signs the user out and
the UI flips by itself. Redirect scheme registered in the Android `manifestPlaceholders` and
iOS `Info.plist`; the browser dance itself is a documented device precondition. `flutter
analyze` clean, 21 tests green — the whole token lifecycle through fakes.

## The one new concept

**`Future`/`async`/`await` — and what a plugin is.** The async half is C#'s model wearing Dart
syntax: `Future<T>` ≙ `Task<T>`, `async`/`await` identical, and `unawaited_futures` (our lint
from 6.1) is the `Task`-dropped-on-the-floor warning. The load-bearing half is the **plugin**:
`flutter_appauth` and `flutter_secure_storage` are Dart facades over a *platform channel* —
an async message pipe into Kotlin/Swift code. That's why their futures exist at all (crossing
the channel is inherently async), why the container can't run them (no platform on the other
end — a `MissingPluginException` in tests), and why both hide behind interfaces: the seam is
not test convenience, it's an honest statement of where Dart ends.

## The mental shift

The 401-refresh interceptor made the state design earn its keep: because the interceptor calls
`refreshAccessToken()` *on the notifier* (not on some token utility), a dead refresh token
doesn't just fail a request — it clears the store, flips the state to `SignedOut`, and every
watcher (the AppBar icon, future guarded screens) reacts **without any screen writing 401
handling**. That's the same insight as 2.x's domain events: put the transition where the state
lives, and the consequences propagate for free. The second shift is respecting the plugin
boundary as an *architectural* line, not a testing nuisance: the phase expansion promised
"container tests fake the token store", and writing it as interfaces made the device-only
surface exactly two small classes — everything else (lifecycle, rotation, sign-out on dead
refresh, claim parsing) is plain Dart proven green here.

## Gotchas hit

- **The shell tests kept passing without overriding the token store** - because
  `SecureTokenStore.read()` throws `MissingPluginException` in the test VM, `AsyncNotifier`
  catches it into `AsyncError`, and the UI's `SignedOut() || null` arm renders the sign-in
  icon. Correct-by-accident graceful degradation; noted so nobody mistakes it for the store
  being exercised - auth tests override BOTH seams explicitly.
- **`unintended_html_in_doc_comment`**: `AsyncValue<AuthState>` in a doc comment parses as an
  HTML tag - backticks fix it. The strict analyzer reads /// comments too.
- The redirect scheme must avoid underscores (`sa.wathiq.wathiqmobile`, not the package name
  verbatim): custom URI schemes with underscores are rejected by some Android browser stacks -
  a device-land bug avoided by reading the appauth docs instead of meeting it.

## Check yourself

1. Why does the Dio interceptor use `ref.read` while `dioProvider` itself uses `ref.watch` for
   the locale?
2. The refresh token comes back rotated (`r1` → `r2`). Walk what the test proves the app does,
   and what would break silently if it didn't.

<details><summary>Answers</summary>

1. `watch` declares "rebuild me when this changes" - right for the locale, whose change should
   produce a NEW client with a new header. Inside interceptor callbacks, `read` is a one-shot
   lookup at request time: a token change must not tear down the client mid-flight, and the
   token is deliberately read fresh per request rather than baked into the client.
2. The test asserts `store.tokens.refreshToken == 'r2'` after refresh: rotation persisted.
   Without it, the NEXT 401 would replay `r1` - which the server already invalidated - so the
   refresh fails, the user is signed out, and the bug looks like "sessions randomly expire
   after exactly one refresh": rotation persistence is the difference between seamless renewal
   and a support ticket.

</details>
