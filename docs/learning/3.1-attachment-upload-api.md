# 3.1 — Attachment upload/download API

> **Phase:** 3 · **App:** backend · **Commit:** `step(3.1): add attachment upload, download and delete endpoints` · **Date:** 2026-08-28

## What was built

The Documents API moves bytes now: three methods on
[DocumentAppService](../../backend/modules/Documents/Wathiq.Documents.Application/Documents/DocumentAppService.cs)
— `UploadAttachmentAsync` (multipart via `IRemoteStreamContent`, MIME **allow-list** checked
before any byte is stored, sha256 computed server-side, `IFileStore` from 1.2 finally consumed),
`GetAttachmentContentAsync` (streams back with the stored content type), and
`DeleteAttachmentAsync` — which keeps the 1.5 promise: `Document.RemoveAttachment` returns the
blob key and the file is deleted in `UnitOfWorkManager.Current.OnCompleted`, i.e. only **after**
the row deletion commits. Upload gets the mirror-image compensation: the `Failed` hook removes a
just-written blob if the transaction rolls back. `DocumentDto` now embeds `attachments[]`
(AutoInclude pays again). **Live proof:** a PNG uploaded through the real API, downloaded
byte-identical (`cmp`), a `text/plain` upload rejected with `UnsupportedFileType`, and after the
DELETE the blob file physically vanished from `App_Data/wathiq-files/documents` (1 → 0 files).
Suites 34 + 30, green. `api.md` v0.1.2 → `out/Api.docx`.

## The mental shift

Files break the tidy transactional world the rest of the app lives in: SQL rolls back, disk does
not. The step's real design content was deciding *when* each file operation may happen relative
to the transaction — and the answer is asymmetric. Deletion must be **late** (post-commit, via
`OnCompleted`): losing bytes is unrecoverable, so the row's fate must be sealed first. Creation
must be **early** (before the insert) but with a **compensation** hook (`Failed`) so a rollback
erases the orphan. Neither hook is exotic ABP — they're the unit of work's own lifecycle — but
choosing which side of the commit each side effect belongs to is the whole discipline, and it
generalizes directly to Phase 8's encryption and to any outbox-style pattern later.

## Gotchas hit

- Docker's daemon needed force-killing twice before the live check: it hung for 30 minutes
  "restoring" containers whose shims died with the previous environment restart — `kill -9` +
  fresh start fixed what waiting would not. (And the self-matching `pkill` bit once more before
  being tamed: the kill command and the start command must never share a shell line.)
- My route guess was wrong *in the good direction*: ABP put `attachmentId` in the path
  (`…/attachment-content/{attachmentId}`), not the query string. Third time the generated spec
  beat an assumption; the api.md tables are copied from the spec, not from memory.
- `RemoteStreamContent` wants a *reset* stream: after hashing, `buffer.Position = 0` before
  handing it to `IFileStore` — forgetting that writes a zero-byte blob and no test would have
  been kind enough to fail loudly without the byte-comparison assertion.

## Check yourself

1. Why is the blob deleted in `OnCompleted` but the upload's blob written *before* the insert
   with a `Failed` compensation — why not symmetric?
2. What two independent gates limit what an upload can be, and in which order do they fire?

<details><summary>Answers</summary>

1. Because the failure costs differ: deleting early risks losing bytes for a row that still
   exists (unrecoverable), while writing early risks an orphan file for a row that never came
   (recoverable — the `Failed` hook, or a cleanup sweep, removes it). Each side effect sits on
   the side of the commit where its worst case is harmless.
2. The MIME allow-list (before any byte is stored — rejects by *claimed* type) and the store's
   `MaxSizeBytes` enforcement while copying (rejects by *actual* size, deleting the partial
   file). Claim first, bytes second.

</details>
