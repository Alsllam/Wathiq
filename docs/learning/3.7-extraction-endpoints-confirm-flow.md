## The mental shift

The confirm endpoint is where "AI feature" quietly becomes "ordinary CRUD" — and that is the
design, not a shortcut. By the time values reach the document they have been (1) validated by
parsers, (2) shown to a human, (3) possibly edited, and (4) pushed through the exact domain
methods a manual edit uses. So downstream (events, reminders, audit) cannot even tell extraction
happened. The AI's entire blast radius is one append-only table. Second shift: **the outcome is
the product's flywheel** — Accepted/Edited/Rejected per prompt version, collected as a side
effect of UX, is precisely the dataset that tells 3.8 whether `extract-document@v2` would be
better or worse.

  settled revival ritual now takes under a minute.

## Check yourself

1. The user confirms a proposal exactly as proposed — but the model had misread the expiry and
   the parser dropped it, so the field arrived empty and the user typed one in. Accepted or
   Edited, and why is that the *right* label for 3.8?
2. Why does `GetLatestAsync` re-run the parsers over `RawJson` instead of the row storing the
   proposal fields as columns?

<details><summary>Answers</summary>

1. Edited — the comparison baseline is the *validated* proposal (expiry = null after the drop),
   and the user supplied a value the system didn't propose. Right for 3.8 because the metric is
   "how often did the pipeline's *output* survive human review unchanged" — and a dropped field
   is part of that output.
2. Warnings aren't persisted and validation rules evolve: storing the raw JSON once and
   re-deriving keeps a single source of truth, lets a parser fix retroactively improve stored
   proposals, and avoids a second schema that could drift from `DocumentDataProposal`.

</details>
