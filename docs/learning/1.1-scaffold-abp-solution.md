## What was built

`backend/Wathiq.slnx`, generated via the ABP CLI (`abp new Wathiq -t app -u no-ui -d ef -dbms
SqlServer --no-multi-tenancy --no-social-logins`): the layered ABP template — `Domain(.Shared)`,
`Application(.Contracts)`, `EntityFrameworkCore`, `HttpApi(.Host/.Client)`, `DbMigrator`, and
three test projects. No custom module yet — this proves the shell: build, migrate, seed, run,
register a new user, and log in both that user and the seeded admin for real access tokens. See
[backend/README.md](../../backend/README.md) for the verified run steps.

## The mental shift

The ABP CLI's own post-generation automation (install libs, create the cert, migrate, seed) is a
`pwsh`-only script chain — on a machine with only Windows PowerShell 5.1, that step silently
fails and leaves you with a solution that *looks* complete but has no migration, no cert, and an
unescaped connection string. Treating "the CLI said it succeeded" as proof of a working solution
would have been wrong; only running the actual chain by hand (build → migrate → run → get a real
token → register a real user) surfaced three separate bugs, each in a different layer (JSON
config, MSBuild package list, a missing options flag for the no-UI host).

## Gotchas hit

- **Empty-folder requirement**: `abp new` refuses to generate into a non-empty directory;
  generated into a scratch dir and moved the result into `backend/`.
- **Invalid JSON connection string**: the `-cs` value's `(localdb)\MSSQLLocalDB` was written into
  `appsettings.json` with a single backslash — `\M` is not a legal JSON escape. `System.Text.Json`
  rejected it, but ASP.NET Core's configuration loader swallowed the failure and just produced an
  empty connection string, surfacing later as `SqlConnection`'s unrelated-looking
  "ConnectionString property has not been initialized." Fixed in both `Wathiq.HttpApi.Host` and
  `Wathiq.DbMigrator` appsettings by escaping to `\\MSSQLLocalDB`.
- **Config resolves from CWD, not project path**: `dotnet run --project src/Wathiq.DbMigrator/...`
  from `backend/` silently loaded no `appsettings.json` (empty config again) because the generic
  host reads config relative to the current working directory. Running `cd src/Wathiq.DbMigrator
  && dotnet run` fixed it.
- **`wwwroot/libs` 500 on every request**: the `-u no-ui` host still ships the MVC client-library
  existence check; added `Configure<AbpMvcLibsOptions>(o => o.CheckLibs = false)` (namespace
  `Volo.Abp.AspNetCore.Mvc.Libs`, found by grepping the installed package DLLs' string heap for
  `CheckLibs` since the compiler error alone didn't reveal which sub-namespace it lived in).
- **Duplicate PackageReference**: `Wathiq.HttpApi.Host.csproj` had `Microsoft.EntityFrameworkCore.
  InMemory` listed twice (NU1504) — a CLI generation quirk; removed the duplicate line.
- **Stale process file lock**: killing the wrong PID (the bash job number, not the actual
  `dotnet.exe` process) left the previous `Wathiq.HttpApi.Host` running and locking its own DLLs,
  breaking the next build with MSB3027. `Get-Process -Name 'Wathiq.HttpApi.Host' | Stop-Process
  -Force` is the reliable way to kill an ABP host started via `dotnet run`.

## Check yourself

1. Why did `abp new`'s own "Initialize Solution" task fail silently, and what did that hide?
2. Which two config keys does `Wathiq_App` need to request a password-grant token, and why does
   it need no client secret?

<details><summary>Answers</summary>

1. It shells out to `pwsh` (PowerShell 7), which isn't installed here (only Windows PowerShell
   5.1 is) — it hid an un-created database, an un-escaped connection string, and a missing
   OpenIddict certificate, all of which "the solution has been created" made look fine.
2. `client_id=Wathiq_App` and `grant_type=password` (plus `username`/`password`); it's seeded as
   an OpenIddict **public** client (`type: Public`, `secret: null`), which is correct for a
   first-party client that can't keep a secret confidential (a mobile app or SPA).

</details>
