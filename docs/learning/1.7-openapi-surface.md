## The mental shift

A running ABP app is assembled from its **module dependency graph**, and each executable (host,
migrator, tests) has its *own* graph — the solution file is irrelevant. The admin-403 bug made
this concrete: the permission *definitions* live in `Documents.Application`, which the host
loads but the DbMigrator didn't. So at seed time, ABP's "grant every defined permission to
admin" contributor saw no Documents permissions at all — while my own 1.6 seeder worked, because
it grants raw constant strings without needing definitions. Same database, same code on disk,
two different graphs → two different behaviours. The rule of thumb that falls out: **whatever a
seeder needs to *see* must be in the seeder process's module graph**, and the migrator needs the
modules that *define* things (permissions, settings), not just the ones that create tables.

## Gotchas hit

- **The admin 403.** Migrator seeded, `user` role had its 9 grants, yet admin got 403 on every
  Documents endpoint — admin's "all permissions" grant only covers permissions *defined* in the
  migrator's module graph. Fix: `DbMigrator` now depends on `WathiqDocumentsApplicationModule`.
  Even after re-seeding, the running host kept answering 403: permission grants are **cached**
  (`IDistributedCache`), so a restart (or cache expiry) is needed after seeding grants directly
  in the DB.
- **`dotnet run` vs. the compiled binary.** `dotnet run` reads `launchSettings.json`
  (`https://localhost:44352`); running `bin/…/Wathiq.HttpApi.Host` directly does not — it bound
  Kestrel's default `:5000` and every request "failed" until `ASPNETCORE_URLS` was set.
  `launchSettings.json` is a *tooling* file, not app configuration.
- **Unauthenticated ≠ always 401.** Without a token the API answered **302** (redirect to the
  hosted login page) until the request carried `Accept: application/json` — ABP content-negotiates
  the challenge. API docs must say this or every curl user will report a "bug".
- **BusinessException maps to 403**, not 400 — ABP's default for domain rule violations
  (`Wathiq.Documents:ExpiryBeforeIssue` came back as 403 with the Arabic message under
  `Accept-Language: ar`). Documented in the error-model table; clients must branch on
  `error.code`, not the status code alone.
- **LocalDB is Windows-only** (`PlatformNotSupportedException` on Linux). SQL Server 2022 in
  Docker (the compose skeleton's image) + `ConnectionStrings__Default` env override made the
  whole stack — migrator, seeding, OpenIddict, live API — work unchanged. First real proof the
  0.6 compose file earns its keep.

## Check yourself

1. `HolderAppService` is C# singular and its Swagger tag is `Holder` — why is the URL
   `/api/documents/holders`?
2. After adding a brand-new permission and re-running the DbMigrator, admin still gets 403 in the
   already-running host. Name both halves of the reason.

<details><summary>Answers</summary>

1. The auto-controller convention derives the segment from the service name; the module sets
   `UrlControllerNameNormalizer` to map each controller name to a plural kebab segment. Only the
   URL changes — class names, tags and DI stay as-is.
2. (a) The migrator only grants *defined* permissions, so its module graph must include the
   module that defines them; (b) the host caches permission grants, so until restart/expiry it
   keeps serving the old "not granted" answer.

</details>
