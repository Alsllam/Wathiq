# 2.5 — Hangfire nightly job

> **Phase:** 2 · **App:** backend · **Commit:** `step(2.5): add the Hangfire-scheduled nightly reminder dispatch job` · **Date:** 2026-08-28

## What was built

[ReminderDispatchJob](../../backend/modules/Reminders/Wathiq.Reminders.Application/Jobs/ReminderDispatchJob.cs)
— a **plain DI class** (no Hangfire types in any module): coarse SQL pre-filter on
`IX_Reminder_Status_DueDate` using the widest today on Earth (UTC+14), then the per-user
time-zone verdict via 2.3's `TodayIn`, then delivery through the new
[IReminderChannel](../../backend/modules/Reminders/Wathiq.Reminders.Domain/Reminders/IReminderChannel.cs)
abstraction (2.6 implements email; tests plug a fake), each outcome recorded as the
`Pending → Sent/Failed` transition. Hangfire (SQL Server storage, 2 workers, dev-only dashboard)
lives **only in the host**, which schedules `RunAsync` as `reminders-nightly` at `0 3 * * *`.
Verified live end-to-end: dashboard trigger → Hangfire job `Succeeded` → log line
`0 sent, 0 failed of 1 candidates` (the candidate was a real due reminder created through the
API; no channel exists yet, so Pending it stays). Tests: run-twice sends once with exactly one
`DeliveryLog`; a poisoned send marks Failed without killing the run. Suites 33 + 21, green.

## The mental shift

The job turned out to be the *least* interesting part — by design. Everything hard was already
owned by someone else: idempotency by the unique index and status machine (2.3), scheduling
correctness by the event sync (2.4), per-user time by `TodayIn`. What remains is a loop with two
disciplines: **no side effect before the state claim**, and **no exception escapes an item**.
That's the payoff of designing the invariant into the data model first — "make the nightly job
safe to run twice" (the 2.CP question) is answered before the job exists, and the job's tests
read like a restatement of the requirement, not a mock choreography. The second insight:
module purity has teeth — because `ReminderDispatchJob` is a plain class, the "Hangfire test"
needs no Hangfire, and the live Hangfire proof needed no test rig, just the dashboard trigger.

## Gotchas hit

- **Middleware order, twice.** `UseHangfireDashboard` placed after `UseConfiguredEndpoints` gave
  `405 Allow: GET, HEAD` on the dashboard's own POSTs — endpoint routing's static-asset
  catch-all owned the request before the dashboard middleware saw it. Moving the dashboard
  before `UseConfiguredEndpoints` fixed it; the `Allow:` header was the diagnostic clue.
- After the order fix: **403** on the trigger POST — Hangfire 1.8 validates an antiforgery token
  on dashboard writes. For a dev-only, local-requests-only dashboard,
  `DashboardOptions.IgnoreAntiforgeryToken = true` is the honest fix (commented as such);
  production exposure is a Phase 7 problem with real auth.
- A `pkill -f` pattern that appears in *other* background shells' command lines kills those
  wrapper shells too (exit 144 noise) — killing by exact binary path with `pgrep`, then `kill`
  by PID, is the calm way.
- The live "1 candidates, 0 sent" line was initially confusing until re-read as correct: the
  host has no `IReminderChannel` implementation yet, so due reminders stay Pending — 2.6 turns
  that same line into "1 sent".

## Check yourself

1. The job never checks "did I already send this?" — no query, no flag. Where exactly does the
   run-twice safety come from?
2. Why is the SQL filter `DueDate <= today+14h` instead of each user's real today, and why is
   that not a correctness bug?

<details><summary>Answers</summary>

1. From the data model: only `Pending` rows are candidates, sending records the
   `Pending → Sent/Failed` transition on the same uniquely-indexed row inside the same UoW, so a
   second run's candidate query simply returns nothing for them.
2. SQL can't cheaply evaluate per-user time zones, so the query over-fetches using the earliest
   calendar on Earth (UTC+14) as an upper bound; the loop then applies the exact per-user
   `TodayIn` and skips rows due tomorrow locally. Over-fetching is filtered, never sent.

</details>
