# 6.7 — Documents list + detail

> **Phase:** 6 · **App:** mobile · **Commit:** `step(6.7): show the signed-in user's documents with expiry chips and attachment details` · **Date:** 2026-09-07

## What was built

UC-01's read side on mobile, authed: the documents tab watches `authProvider` and — signed out —
renders an *invitation* with a sign-in button (not an error, not an empty list; the 5.7 chat
gate pattern). Signed in: rows show the localized type name (from the anonymous type-catalogue
provider, mapped by id), the number, and an **expiry chip** driven by the portal's exact
severity rules — `expirySeverity` ported as a pure function over the *server-computed*
`daysUntilExpiry`, so both apps agree by construction, no duplicated date math. The detail page
(`/documents/:id`, deep-linkable like guides) shows dates, notes and the attachments list —
which forced `AttachmentModel` into 6.2's model (the wire had it; the model didn't). Bearer
auth rides invisibly: the 6.6 interceptor supplies WHO, the API owner-scopes WHAT. `flutter
analyze` 0 issues, 25 tests green.

## The one new concept

**`ConsumerWidget` vs `StatefulWidget` — when local state earns a `State` object.** This step
answers by construction: *both new screens are plain `ConsumerWidget`s*, because everything
they show derives from providers (auth state → gate, documents → rows, types → names, locale →
which name). The codebase now holds the whole decision table: `HomeShell`'s tab index and the
guide detail's `_flagged` are `State` material — ephemeral, pre-save, single-widget concerns —
while anything a second consumer might need, or that survives the screen, lives in a provider.
The portal's analogue: a component with only `computed`s needs no writable signals; the rule
here is the same, with `State` playing the writable's role.

## The mental shift

The auth gate wrote itself, and noticing *why* was the lesson: 6.6 put the transition where the
state lives, so this screen just pattern-matches `SignedIn`/`SignedOut` and never thinks about
tokens, 401s, or refresh — three steps of infrastructure collapsing into one `switch`. The
second realization was about the `!` operator: after five steps of treating nullability as
sacred, the expiry chip hit the one legitimate case — `severity == ok` *implies*
`expiryDate != null` because the server derived one from the other — and the honest move isn't
avoiding `!` with defensive fallbacks that hide bugs, but using it WITH the invariant written
down. Null safety isn't "never assert"; it's "every assertion is visible and justified".

## Gotchas hit

- **6.2's model was missing `attachments` entirely** - the captured list payloads didn't
  include them prominently and the field slipped. The detail screen's needs caught it; the
  fix extends the model + fromJson with a defaulted `const []`. Models built from captured
  payloads inherit the payloads' blind spots - the step that CONSUMES a field is the real test.
- Wrote a `List<Override>`-typed helper again out of reflex (the exact 6.4 mistake), caught it
  before the analyzer did this time, and left a `_pump` helper taking domain arguments instead
  - the second time a lesson repeats, encode it in the shape of the helper.
- `intl`'s Arabic plural rules make `expiresInDays(7)` render "خلال 7 يومًا" from one ARB
  entry - the test asserts the real rendered string, not the template.

## Check yourself

1. Why does the signed-out documents tab render an invitation rather than letting the API
   return 401 and showing the error state?
2. The expiry chip uses `doc.expiryDate!` in the `ok` arm. Defend it against the "never use
   `!`" reflex.

<details><summary>Answers</summary>

1. A 401 is the MECHANISM, not the message: the user's situation is "this feature needs an
   account", best said before any request is wasted (and the cap never touched). Watching the
   auth state renders the truthful UI instantly and keeps the error state meaning what it
   says - "the load failed" - instead of doubling as a disguised login wall.
2. `daysUntilExpiry` is server-DERIVED from `expiryDate`: ok-severity (days > 30) cannot exist
   without a date. The alternatives are worse: a fallback date lies to the user; restructuring
   the model to carry proof burdens every other screen. `!` with the invariant commented is
   the assertion in its honest form - and if the server contract ever breaks it, the crash
   points at the exact violated assumption instead of rendering garbage.

</details>
