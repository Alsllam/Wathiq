# 5.4 — Retrieval: cosine top-k over SQL-stored embeddings

> **Phase:** 5 · **App:** backend · **Commit:** `step(5.4): retrieve top-k guide chunks by in-process cosine with a hydrated cache` · **Date:** 2026-09-03

## What was built

`IGuideRetriever`: embed the question through the same local generator as the corpus, score it
against the **served** chunks with plain cosine, return top-k above a similarity floor — with an
**empty list as a first-class answer** (the refusal signal 5.5 turns into an honest "no
answer"). The kernel is `VectorMath.CosineSimilarity` — ten lines, double accumulation,
zero-vector and dimension-mismatch semantics pinned by tests. Around it: a singleton
`GuideChunkCache` that hydrates SQL's `varbinary` blobs into `float[]` once (TTL 5 min, plus
explicit invalidation from the embed job), the served-corpus scope (active guides, latest
published version per language — superseded versions' chunks stay in SQL for citations but stop
being candidates), the `EmbeddingModel` filter (5.3's provenance column now doing its job), and
`GuideRetrievalOptions` (topK/floor/TTL as config knobs, tuned by 5.6's evals).

## The mental shift

Writing retrieval without a vector database dissolved the mystique: **retrieval is a read model
plus a ranking function.** The read model (which chunks are candidates) took more design than
the math — served-versions-only, active-guides-only, same-model-only are all *product* decisions
that a `SELECT ... ORDER BY VECTOR_DISTANCE(...)` would have buried inside a query string. The
ranking function is ten auditable lines. And the floor changed how I think about scores: it is
not a quality knob but a **refusal boundary** — everything below it is "the corpus does not
speak to this question", which 5.5 must surface as exactly that. Choosing `0.5` today is
explicitly provisional; the 5.6 eval set exists to move it with evidence instead of vibes.

## Gotchas hit

- The cache is a **collection-wide singleton in tests**: earlier test classes in the same
  SQLite collection warm it with their corpus, so the retriever tests invalidate in the
  constructor — the 3.5 order-dependence lesson, now recognized *before* it produced a flaky
  test rather than after.
- Asserting rankings with random-ish fake vectors is a trap: the deterministic
  `FakeEmbeddingGenerator` makes "question == chunk text" score exactly 1.0, so tests assert
  the *provable* things (exact text ranks first, scores descend, floors/topK bound the list)
  and never "chunk B beats chunk C" claims that depend on hash accidents.
- `GuideRetrievalOptions` binds `TimeSpan` from config ("00:05:00") - worth remembering that
  the binder parses TimeSpan natively; no custom converter, no seconds-as-int workaround.

## Check yourself

1. Why does the retriever filter chunks by `EmbeddingModel` instead of letting a wrong-model
   chunk simply score low?
2. A guide gets re-authored and republished. Walk what happens to the old version's chunks in
   SQL, in the cache, and in citations of past answers.

<details><summary>Answers</summary>

1. Vectors from different models don't share a space - a cosine between them is not "low", it
   is MEANINGLESS, and could accidentally be high. Filtering makes wrong-model chunks invisible
   until re-embedded (the rebuild-embeddings lever), which fails safe: missing answers, never
   wrong ones.
2. In SQL: the chunks stay (the version is immutable and its rows are the citation anchors).
   In the cache: the embed job for the NEW version invalidates, and the next load's served-set
   computation (latest published per guide+language) excludes the old version - its chunks stop
   being retrieval candidates. Citations: past answers cite chunk/version ids that still
   resolve to exactly the text they cited - stable history, fresh retrieval.

</details>
