# 4.6 — Add-document wizard I: create + upload

> **Phase:** 4 · **App:** frontend (+1 auth-lib addition) · **Commit:** `step(4.6): build the add-document wizard on hand-rolled signal forms` · **Date:** 2026-08-30

## What was built

`documents/new`: a three-step wizard whose entire form layer is a DOM-free class of signals and
computeds (`AddDocumentWizardState`) — the honest resolution of the roadmap's "signal forms"
(the experimental `@angular/forms/signals` API is v21+; checked, not assumed): fields are
signals, step validity is `computed`, `ExpiryBeforeIssue` is mirrored client-side, and the
server's MIME/size allow-list is pre-checked before a byte uploads. Upload progress is
`HttpClient`'s event stream bridged into a signal. The step's surprise chapter: browser POSTs
hit ABP's **antiforgery** wall (twice), fixed properly in the auth lib. **Proven live**:
Playwright walked login → wizard → type/holder → fields → PNG → landed on the new document's
detail (`DL-2026-777`, valid 3624 days, 13 KB attachment). 22 unit tests, lint, build green.

## The mental shift

A wizard is a **state machine wearing a form costume** — and once the machine is a plain class
of signals, the framework question ("which forms API?") almost disappears: `[value]` +
`(input)` is the entire binding story, validity is just derivation, and the spec walks
steps/blocks/backtracks without ever mounting a component. The antiforgery saga carried the
deeper lesson: **the browser is a different client than curl**. Every backend proof so far rode
Bearer-only requests; the first real browser POST brought cookies along (ports don't scope
them), flipping ABP into cookie-auth rules nobody had exercised. "Works with curl" verifies the
API; only a browser verifies the *application*.

## Gotchas hit

- ABP antiforgery, round one: POST → bare 400, empty body, no validation error — the log's
  `AbpAutoValidateAntiforgeryTokenAuthorizationFilter` line was the only clue. Round two after
  adding the header: "token was meant for a different claims-based user" — antiforgery tokens
  bind to the principal, and ours was minted anonymous. Fix: `xsrfInterceptor` (cookie →
  `RequestVerificationToken` header) + re-issuing the cookie post-login via ABP's own
  `application-configuration` call — the two halves ABP's Angular package quietly does for you.
- The e2e clicked 'رخصة القيادة'… in the shell's catalogue preview, not the wizard — the same
  text exists twice on the page. Scoping every selector to `wq-add-document-wizard` fixed it;
  ambient text is not a selector.
- The a11y lint (`label-has-associated-control`) rejected `<label>` as button-group captions —
  correctly: two became `<p>`, the file input got a real `for`/`id` pair.
- `@angular/forms@20.3` has no `signals` entry point — verified by listing the package rather
  than trusting release-note memory, per 4.0's plan.

## Check yourself

1. Why does `AddDocumentWizardState` live outside the component, and what does that buy the
   4.7 step concretely?
2. Reconstruct the antiforgery chain: why did every 1.7–4.5 verification miss it, and why did
   the fix need *two* parts?

<details><summary>Answers</summary>

1. It is the wizard's domain logic - component-free, it specs without TestBed, and 4.7 extends
   the same machine (a review step consuming the extraction proposal) by adding signals and
   computeds, not by refactoring a template-bound form.
2. All prior verifications were curl/HttpClient with Bearer only - no cookies, so ABP never
   engaged its cookie-auth antiforgery. A real browser sends the localhost login cookie with
   proxied API calls (cookies ignore ports). Part one: send the XSRF cookie back as the
   `RequestVerificationToken` header. Part two: re-issue that cookie after login, because the
   token is bound to the principal and the pre-login one was anonymous.
