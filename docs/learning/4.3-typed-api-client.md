## The mental shift

`httpResource` moves HTTP from *imperative act* to *derived state*: the URL is a computed
function, so when its signal inputs change the fetch re-happens — data is something you
*declare from* state, like a `computed`. That reframing has a testing consequence I hit head-on:
a pending resource **holds app stability** (it registers a pending task), so the familiar
`await whenStable()` deadlocks against a stubbed backend that is waiting to be flushed. The
order is now: `detectChanges()` (effects run, request issued) → flush → `whenStable()`. Second
shift: checking the generated file *and* its source spec into the lib makes API drift a
reviewable diff — regenerating on a backend change shows exactly which types moved, the same
way a migration diff shows schema drift.

## Gotchas hit

- All three portal tests suddenly timing out on `whenStable()` — not a bug in the tests'
  subjects but the embedded `httpResource` keeping the app un-stable until its request was
  answered (`document-types-preview.spec.ts:35` documents the required order). The App spec
  needed a `flushCatalogue()` helper for the same reason: composition changed the stability
  contract of every existing test.
- The roadmap's "(anonymous endpoint)" was written from memory and wrong — `DocumentTypes.Default`
  guarded the list. Checked the attribute *before* building the smoke on it; the honest options
  were "change the product" or "change the step", and public-reference-data won.
- ABP swagger schema ids are full .NET type names (`Wathiq.Documents.DocumentTypes.DocumentTypeDto`)
  — usable but hostile as an import surface; the lib's `index.ts` aliases exactly the DTOs the
  app consumes, with the alias list grep-verified against the generated file.
- The proxy targets the *canonical* dev port (44352 from `launchSettings.json`), not whatever
  port this session's host happened to be on — config committed to git must be true on the dev
  box, so the live probe moved the host to the config instead of bending the config to the
  session.

## Check yourself

1. Why check the generated `api-types.gen.ts` into git when a script can always regenerate it?
2. A test renders a component containing `httpResource` and hangs on `whenStable()`. Walk the
   deadlock and its resolution.

<details><summary>Answers</summary>

1. Reproducibility and reviewability: the build never depends on a running backend, and a
   regeneration after a backend change produces a *diff* — the frontend twin of reviewing a
   migration instead of trusting `dotnet ef` blindly. The committed spec pins which contract
   version the types came from.
2. The resource registers a pending task until its request completes; `whenStable()` awaits no
   pending tasks; the testing backend holds every request until `flush()` — but the request is
   only issued once effects run. So: `detectChanges()` to run effects and issue the request,
   `expectOne().flush()` to complete it, and only then `await whenStable()`.

</details>
