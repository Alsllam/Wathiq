## The mental shift

Two value objects, two persistence strategies, and the choice is *not* stylistic. `ValidityPeriod`
became columns (owned type) because SQL needs to index and compare `ExpiryDate` — the database
must see *inside* the value. `ReminderOffsets` became one CSV column (conversion) because no
query will ever filter "rules where an offset = 30"; the database only stores and returns it,
and the domain does all the thinking. The rule of thumb that crystallized: **let the query needs
of the column decide the mapping, not the shape of the C# type.** And a conversion drags in an
obligation ownership doesn't: the `ValueComparer`, because EF's change tracker can no longer see
into the value on its own.

## Gotchas hit

- The first `dotnet-ef migrations add` was written into the doc from memory of the timestamp and
  was wrong by 14 seconds (`…0756` vs the real `…0810`) — migrations-log entries get copied from
  `ls Migrations/`, not typed.
- `ValueComparer<ReminderOffsets>` has a nullable-reference wrinkle: the equality lambda must
  handle both sides null (`(a, c) => (a == null && c == null) || (a != null && a.Equals(c))`) or
  the compiler warns and the comparer can throw during snapshotting.
- `TimeOnly` needed **zero** configuration — EF Core maps it to SQL `time` natively now; the
  temptation to add a converter (as older blog posts show) is out of date.
- The 2.1 warning (`No instantiatable types implementing IEntityTypeConfiguration…`) disappeared
  from the migrator log exactly as predicted — worth noticing as the *absence* of a symptom.

## Check yourself

1. Why does `ReminderOffsets` get `HasConversion` while `ValidityPeriod` got `OwnsOne`?
2. What breaks if the `ValueComparer` is omitted from the offsets mapping, and when would you
   notice?

<details><summary>Answers</summary>

1. Query needs: `ExpiryDate` must be indexable/filterable as its own column, so the value object
   flattens into columns; nobody queries inside the offsets list, so it can travel as one scalar.
2. EF snapshots the property by reference. Replacing the value object still works (new
   reference), but the comparer's real jobs — detecting *equality* to skip no-op updates and
   producing correct snapshots — silently degrade: typically every save issues an UPDATE for an
   unchanged row, first noticed as audit noise (`LastModificationTime` churn).

</details>
