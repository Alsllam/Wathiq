# 4.7 — Add-document wizard II: extraction review → confirm

> **Phase:** 4 · **App:** frontend · **Commit:** `step(4.7): close UC-01 for humans with the extraction review panel` · **Date:** 2026-08-30

## What was built

`ExtractionReview`, embedded under every *image* attachment on the detail page (PDFs get an
honest "not available yet" line, mirroring 3.5's server): a five-phase signal state machine —
idle → waitingOcr → extracting → review → concluded/failed. `ExtractionNotReady` auto-retries on
a **visible countdown** (OCR readiness only surfaces through the extract attempt — the roadmap's
"poll latest" adjusted to the API's real shape, noted for the architecture doc). The review
phase shows FR-AI-003's warnings beside pre-filled editable fields; confirm/reject drive 3.7's
endpoints and `concluded` triggers the parent's `document.reload()`. **Proven live in a
browser**: upload → immediate extract → countdown → auto-retry → OCR landed → model absent →
the mapped Arabic `ExtractionFailed` message — and the `Failed` row (outcome=4) in SQL from that
very click. 23 unit tests, lint, build green. Happy path = dev box with Ollama.

## The mental shift

UC-01 closes not with the happy path but with a **survivable everything-else**: the state
machine's five phases are really five answers to "what does the user see when X isn't ready /
broke / ran out?" — and building them first meant the live e2e could prove the whole machine in
a container that *cannot* run the happy path. That inversion (the failure paths are the testable
product; success is one more transition) is the same honesty 3.4 applied to environments, now
applied to UX. Second: the review panel is where the system's distrust of the model becomes the
user's *trust* in the system — the warning saying exactly why a field is empty is 3.6's parser
speaking directly to the human who must now fill it.

## Gotchas hit

- Fake timers deadlocked `whenStable()`: the zoneless scheduler itself schedules via timers, so
  freezing time freezes "stability" — the retry test asserts signals right after synchronous
  HTTP flushes instead. A zoneless-specific twist on a classic jest trap.
- The roadmap said "poll `latest` until OCR lands", but no endpoint exposes OCR status — it
  surfaces only as `ExtractionNotReady` on the extract attempt. The poll became a visible
  retry-of-extract; recorded as an API-shape observation (a `GET ocr-status` or a field on
  `AttachmentDto` would let the UI show "reading…" before the first click) rather than silently
  bending the UI around it.
- The e2e's race was embraced, not fought: clicking extract immediately after upload can land
  before OR after the OCR job. The script logs which path ran instead of sleeping until one is
  guaranteed — this run hit the good one (countdown visible, auto-retry, then the model error).

## Check yourself

1. Why does the countdown live in the UI at all — what would be wrong with silently retrying
   every 8 seconds until extraction succeeds?
2. The `concluded` output carries no payload. What would passing the updated document through it
   have broken?

<details><summary>Answers</summary>

1. Two things: honesty (the user learns their document IS uploaded and reading is in progress -
   not that something hangs), and boundedness (MAX_AUTO_RETRIES stops a dead OCR pipeline from
   polling forever; the failed state then offers a manual retry). Silent polling hides both the
   progress and the giving-up.
2. Ownership: the detail page's `httpResource` is the single source of truth for the document;
   a payload would create a second, possibly divergent copy (and skip server-computed fields
   like `daysUntilExpiry`). Announce-and-reload keeps one owner per piece of state - the same
   reason 2.4's event carries ids, not entities.

</details>
