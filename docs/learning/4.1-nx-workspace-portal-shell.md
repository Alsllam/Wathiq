## What was built

The Nx 21.6 workspace under `frontend/` (created by the generator, merged in so the layout
README survives — and the generator's nested `.git` removed before it became an accidental
submodule). `wathiq_portal` is Angular 20.3, standalone, **zoneless from the first commit**:
`zone.js` uninstalled, empty polyfills, test env switched to the zoneless setup. Tailwind 4
wired the v4 way (PostCSS plugin + one `@import`, no config file). Module-boundary

green, built CSS contains our utilities, and `nx serve` answered with `dir="rtl"`, the Arabic
title and a 200 stylesheet.

## The mental shift

Zoneless inverts the default answer to "how does Angular know something changed?" — from
"zone.js saw *some* async work, so check everything" to "a signal you read in a template told
us, so check that view". That is why the shell's static title is a signal anyway: under
zoneless, plain fields are the escape hatch, not the norm, and building the habit on day one is
the point of doing this before any real screen exists. The second shift is Tailwind 4's: the
config file didn't move, it *dissolved* — content scanning is automatic and the theme is CSS,
so "setup" collapsed to five lines across two files.

## Gotchas hit

- Writing `ms-*/me-*` inside a CSS comment: the `*/` in the middle *terminates the comment* —
  the build failed with "Unknown word me-\*" from the angular-css plugin. Prose about glob-ish
  utilities inside CSS comments needs the stars dropped.
- The generator scaffolds zone-ful by default (zone.js polyfill + `provideZoneChangeDetection`
  + zone test env) — going zoneless is three coordinated edits (config provider, polyfills
  array, test setup), and missing the third would have tests running under a different CD model
  than production.
- `create-nx-workspace` cannot target a non-empty directory, so the workspace was created in
  the scratchpad and moved — same filesystem, so `node_modules` moved for free — while keeping
  our layout README and deleting the generator's `.git` (a nested repo silently breaks the
  parent's tracking of everything under it).
- `jest-preset-angular` 14.6 already ships `setup-env/zoneless` — no zone.js needed anywhere in
  the dependency tree once the polyfill went.

## Check yourself

1. Why does removing `zone.js` require touching the *test* setup, and what breaks (and how
   visibly) if you forget?
2. The boundary rules name tags (`type:feature`, `scope:shared`) that no project carries yet.
   What is the argument for shipping the constraints in 4.1 anyway?

<details><summary>Answers</summary>

1. `setupZoneTestEnv` imports zone.js, which is no longer installed — so it fails loudly at
   import. The subtle risk is the opposite fix (keeping zone.js only for tests): tests would
   pass under zone-based CD while production runs zoneless, hiding exactly the missed-signal
   bugs zoneless is supposed to surface.
2. The 3.3 privacy-wall argument: a constraint added after code exists is a constraint you hope
   nobody already violated. Declared now, the first lib generated with the wrong tag or the
   first app-to-app import fails lint immediately — the boundary teaches instead of archaeology.

</details>
