## The mental shift

An integration test through the app service is testing a *different thing* than the 1.7 curl
session, even when both create a document. The live test proved the **wiring**: routes, tokens,
grants, caches — and it found a wiring bug (the migrator's graph). The integrated test pins the
**behaviour** under everything replaceable: it will keep passing (or start failing) as the schema,
services and rules evolve, with no server, no Docker, in milliseconds per test after boot. That's
why always-allow auth in tests is not cheating: grants are configuration proven live once, while
ownership is *logic* — so the test suite fakes the former and asserts the latter. And the
self-holder test read differently than expected: the "arrange" step (`holders.GetListAsync()`)
*is* an assertion, because first-use materialisation is itself FR-DOC-007 behaviour.

## Gotchas hit

- `Wathiq.Application.Tests` references the host's Application project, which does **not** carry
  `Documents.Application` — left alone, `IDocumentAppService` would never resolve in the test
  host. Same disease as 1.7's admin-403; this time it was caught by reading the module graph
  *before* the first run: add the project reference *and* the `[DependsOn]`.
- The fake principal in `Wathiq.TestBase` pins one hard-coded admin user for every test; per-user
  scenarios need `ICurrentPrincipalAccessor.Change(...)` — it nests and restores on dispose,
  which is exactly what the two-user ownership test needs on a single xUnit thread.
- The step's text asked for a domain test for `ExpiryDate` validation, but 1.5 already shipped
  `ValidityPeriodTests` — the honest move was to *not* write a duplicate and record that here,
  rather than pad the diff.
- `database.md` needed nothing: appending the migrations log in the same commit as each
  migration (the 0.5 rule) means the phase-end "close the loop" is a verification, not a chore.

## Check yourself

1. The integration test never checks a permission, yet 1.7 proved permissions matter. Why is
   `AddAlwaysAllowAuthorization` in the test base still the right call?
2. Why does the ownership test assert `EntityNotFoundException` instead of a forbidden/authorization
   exception?

<details><summary>Answers</summary>

1. Grants are configuration (seeded rows + cached checks) — proven once against the live host in
   1.7. The suites test *logic* that changes with every commit; always-allow keeps them fast and
   focused, and a permission regression would surface in the live/Swagger path, not silently.
2. Because the service deliberately translates "exists but not yours" into "not found"
   (`GetOwnedAsync`): a 403 would confirm a guessed id exists. The test pins the security
   behaviour, not the HTTP mapping.

</details>
