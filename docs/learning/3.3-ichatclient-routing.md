# 3.3 — Provider routing behind `IChatClient`

> **Phase:** 3 · **App:** backend · **Commit:** `step(3.3): route AI providers behind keyed IChatClients with usage tracking and caps` · **Date:** 2026-08-28

## What was built

The privacy wall and the meter, before any model exists. Two **keyed** `IChatClient`s
("extraction", "guides") are registered by
[WathiqAiApplicationModule](../../backend/modules/Ai/Wathiq.Ai.Application/WathiqAiApplicationModule.cs)
from the host's `Ai` config section — the only place provider SDK types (OllamaSharp) are
allowed. [AiOptions.Validate](../../backend/modules/Ai/Wathiq.Ai.Domain/AiOptions.cs) is
FR-AI-002 as a startup guard: a cloud provider on the extraction client **kills the boot**.
Around every inner client sits
[UsageTrackingChatClient](../../backend/modules/Ai/Wathiq.Ai.Application/Clients/UsageTrackingChatClient.cs)
(a `DelegatingChatClient`): the FR-AI-004 daily cap is checked *before* the call leaves the
process, and one `AiUsage` ledger row is written afterwards in a `requiresNew` unit of work —
proven by a test that rolls back the ambient transaction and still finds the row. Callers can
announce a prompt version through `ChatOptions.AdditionalProperties` without this layer knowing
prompts. **Live, both directions:** `Ai__Extraction__Provider=groq` → boot refused with the
FR-AI-002 message; the ollama config → host up. Suites 36 + 34, green.

## The mental shift

The wall is *config validation*, and that's what makes it strong. My first mental model of
FR-AI-002 was "be careful which client you inject" — a discipline. The implemented version is a
*structure*: extraction consumers can only name a key, the module maps keys to providers, and
the mapping refuses to exist in an illegal state (boot dies). Discipline degrades with every new
contributor; structure doesn't. The same inversion applies to the cap: it isn't "remember to
check usage" in every AI feature, it's a decorator that every client is born wrapped in — the
features can't forget because they never knew. Cross-cutting requirements earn their guarantees
by moving *down* the stack, from call sites into composition.

## Gotchas hit

- The `ObjectDisposedException` on `AiDbContext`: repository *extension* methods
  (`CountAsync(predicate)`, `AnyAsync`) call `GetQueryableAsync()` — an interface call whose
  interception-created transient UoW completes on return, disposing the context the queryable
  still points at. Invisible inside app services (ambient UoW exists); fatal in a decorator
  running UoW-less. Fix: the cap check begins its own UoW. Every earlier use of these
  extensions happened to sit inside an app-service UoW — luck, now understood.
- `Microsoft.Extensions.AI` went 10.x (10.9.0) and the old `Microsoft.Extensions.AI.Ollama`
  package is deprecated — OllamaSharp (5.4.30) is the maintained `IChatClient` implementation;
  `dotnet add package` picked both versions instead of me guessing from stale memory.
- The negative live test needed care to not be theater: the *same binary* that boots with
  ollama config refuses with `Ai__Extraction__Provider=groq` — one env var flips the outcome,
  proving the guard reads real configuration, not a hardcoded happy path.

## Check yourself

1. Why does the extraction client's provider restriction live in `AiOptions.Validate()` at boot
   rather than as a check inside the extraction code path?
2. The ledger write uses `requiresNew` while the cap check uses a plain `Begin`. Why the
   difference?

<details><summary>Answers</summary>

1. A runtime check guards one code path and can be forgotten in the next one; the boot guard
   makes the illegal configuration unrepresentable in a *running* system — every future
   extraction feature inherits the wall for free, and a config typo is caught at deploy, not
   after documents leaked.
2. The cap check is a read: it just needs a live DbContext, and joining any ambient UoW is
   fine. The ledger write must *commit independently* of the caller's transaction — accounting
   survives rollbacks — which is exactly what `requiresNew` provides.

</details>
