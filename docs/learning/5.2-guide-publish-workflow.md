# 5.2 — Guide entities + publish workflow

> **Phase:** 5 · **App:** backend · **Commit:** `step(5.2): add Guide/GuideVersion/GuideStep with immutable publish workflow and seeded passport guide` · **Date:** 2026-09-03

## What was built

The content spine of Phase 5: `Guide` (stable identity: slug + titles), `GuideVersion` (one
authored snapshot — language, markdown body, mandatory `LastVerifiedAt`, nullable `PublishedAt`)
and `GuideStep` (ordered children of the version aggregate), per the DB doc. The module's core
rule lives in the domain: **a published version refuses every mutation** — `UpdateDraft` and
`ReplaceSteps` both pass through `EnsureDraft()`, because 5.3's chunks and 5.5's citations will
point at `GuideVersionId`s. Publish is a one-shot freeze that re-points
`Guide.PublishedVersionId` (latest publish wins). On top: `GuideManager` (slug uniqueness, one
`VersionNo` timeline per guide, the two-aggregate publish handshake), admin authoring endpoints
behind `Guides.Manage`, an anonymous reading surface, and a **real seeded guide** — passport
renewal, ar + en, both published, 12 steps. Verified end to end over HTTP: anonymous
`by-slug` returns the Arabic content with its freshness date; anonymous authoring is denied;
an admin bearer token creates and drafts; drafts never appear publicly.

## The mental shift

Modeling the publish workflow forced a distinction I'd been blurring: **identity vs content**.
`Guide` is identity (a slug that URLs and future links hang off), `GuideVersion` is content (a
frozen, citable snapshot), and almost every design question answered itself once assigned to the
right side — titles are identity (they name the thing in both languages), `LastVerifiedAt` is
content (a fact about one snapshot's freshness), language is content (one guide, one slug, ar
and en *versions*). The single `PublishedVersionId` pointer plus "latest published per language"
at read time turned the would-be schema question ("two pointers? a junction table?") into a
query — the schema stays exactly as the DB doc drew it. And the immutability rule earns its
keep before RAG even arrives: the public read path can serve `GuideVersion` content with zero
defensive copying because nothing can change it.

## Gotchas hit

- **The seed killed all 50 EF tests at startup** — `EntityNotFoundException: Guide` from inside
  `GuideManager.CreateDraftAsync`. The seed runs create → draft → publish in ONE unit of work;
  `InsertAsync` without `autoSave` only stages the row, and the next step's `GetAsync(id)` is a
  real SQL query that finds nothing. Fix at `GuideManager.cs:44` and `:63` (`autoSave: true`) —
  the 3.6 cross-aggregate-ordering lesson, third appearance, now commented at the line.
- **Guessed route, honest 404**: I curled `/by-slug/renew-passport` and got 404 with the host
  healthy. ABP's conventional routing only puts a parameter named `id` in the path — everything
  else is query string: `/api/guides/guide/by-slug?slug=…&language=…`. Swagger, not memory, is
  the route authority (the 1.7 ritual paying out again).
- **`FullAuditedAggregateRoot` means soft delete** — remembered from the OpenIddict tombstone
  incident *before* it bit this time: cleanup of the HTTP smoke-test guide used raw SQL DELETE,
  and any future "remove guide" feature must expect filtered queries, not missing rows.

## Check yourself

1. Why is `Guide.PublishedVersionId`'s FK configured `NoAction` when every other child FK in
   the module cascades?
2. The seed calls `GuideManager` instead of inserting entities directly. What did that decision
   catch, and what does it guarantee going forward?

<details><summary>Answers</summary>

1. `GuideVersion.GuideId` already cascades Guide→GuideVersion. `PublishedVersionId` points the
   other way (Guide→GuideVersion as a reference); making it cascade too would give SQL Server
   a second cascade path between the same tables, which it rejects at migration time. NoAction
   is also semantically right: deleting a version must never silently delete the guide.
2. It caught the autoSave ordering bug (create→read-back inside one UoW) because the seed
   exercised the exact call sequence the admin endpoints use - a hand-rolled INSERT would have
   worked and hidden the bug until the first real authoring session. Going forward it guarantees
   seeded content obeys every domain rule (slug shape, language set, immutability) - the seed
   can never produce states the domain forbids.

</details>
