## The mental shift

Slicing RAG made its real dependency structure visible: everything interesting hangs off
**"what exactly does a citation point at?"** — answer that first (an immutable `GuideVersion`,
5.2) and chunking, embedding, retrieval and citation validation all become straightforward
consumers of that anchor. Slice the other way (start from "chat with the model") and every
earlier layer gets rebuilt when versioning arrives. The second realization: the eval design
(5.6) was co-written with the feature list — must-refuse questions exist because 5.5 makes
refusal a behavior, which only happened because the eval step forced the question "how would we
even score groundedness?" backwards into the design.

## Check yourself

1. Why must 5.2's "published versions are immutable" rule land before any embedding work?
2. Which parts of the grounded-chat step (5.5) are verifiable in this container without any
   model, and why is that list surprisingly long?

<details><summary>Answers</summary>

1. Chunks and their embeddings reference a `GuideVersionId`; if a published version could be
   edited in place, stored embeddings and past answers' citations would silently describe text
   that no longer exists. Immutability makes the version a stable anchor - re-authoring means a
   new version, new chunks, new embeddings, and the old citations stay true of what they cited.
2. Everything except the model's prose: the prompt file's existence/versioning, the citation
   validator (hallucinated ids dropped), the similarity-floor refusal path, the endpoint's error
   codes and caps, and `LastVerifiedAt` riding every answer - because 3.6 established that the
   parser/validator layer, not the model, is where correctness lives.

</details>
