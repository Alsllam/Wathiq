## What was built

The first custom module, `backend/modules/Shared/Wathiq.Shared/` — a single project with no
entities and no database: [IFileStore](../../backend/modules/Shared/Wathiq.Shared/Files/IFileStore.cs)

## Topics applied

| Topic | Where in the code | What I already knew it maps to (Angular / ABP / other) |
| --- | --- | --- |
| Cross-cutting module with no aggregates | `Wathiq.Shared.csproj` — only `Volo.Abp.Localization` referenced | An Nx `shared/util` lib: no state, no HTTP, just services other libs import |
| Leaf module in the dependency graph | `WathiqSharedModule.cs` has no `[DependsOn]` on business modules; `WathiqDomainModule` depends on it | `enforce-module-boundaries`: `shared` may be imported by feature libs, never the reverse |

| ABP virtual file system for embedded JSON | `AddEmbedded<WathiqSharedModule>()` + `AddVirtualJson("/Localization/WathiqShared")` | Assets bundled into the lib and read by path, like Transloco loading `assets/i18n/*.json` |
| Localized exceptions via error codes | `WathiqSharedErrorCodes` + `MapCodeNamespace("Wathiq.Shared", …)` | The reference backend throws plain strings; here the code is the key, and the client gets the text in its `Accept-Language` |
| Abstract-then-concrete test pattern | `LocalDiskFileStoreTests<T>` (Domain.Tests) → `EfCoreLocalDiskFileStoreTests` (EFCore.Tests) | Same as the template's `SampleDomainTests`: the domain test project owns the assertions, the EF test project owns the runnable host |

## The mental shift

A module's *package list* is its boundary statement. `Wathiq.Shared` referencing only
`Volo.Abp.Localization` (which drags in Core, VirtualFileSystem, ExceptionHandling) means it
physically cannot map an entity or open a `DbContext` — the compiler enforces "Shared has no
data". Conversely, the file store is consumed through `IFileStore` only, so Phase 8's encryption
and any later S3 backend are implementation swaps that no other module will notice.

## Gotchas hit

- **`Volo.Abp.Core` is not enough.** `AbpLocalizationOptions`, `AbpVirtualFileSystemOptions` and
  `AbpExceptionLocalizationOptions` are not in Core; the errors listed 21 missing types. Verified
  by grepping the extracted `Volo.Abp.Core.dll` (only `ITransientDependency`/`BusinessException`
  hit) — referenced `Volo.Abp.Localization` instead.
- **No `ImplicitUsings` in the ABP template**, so `Stream`/`Task`/`CancellationToken` need
  explicit `using System.IO;` etc. in every file.
- **`GetConfiguration()` lives in `Microsoft.Extensions.DependencyInjection`** (ABP extension),
  not in `Microsoft.Extensions.Configuration`.
- **Embedded JSON silently not found.** The resource registered (the `/api/abp/application-localization`
  response had a `WathiqShared` key) but its `texts` were `{}` in both cultures.
  `GenerateEmbeddedFilesManifest` only emits a manifest when the project references
  `Microsoft.Extensions.FileProviders.Embedded` — the template's `Domain.Shared` has it, my new
  csproj did not. Added it; then the new localization test (and the host) returned the Arabic text.
  Lesson: an empty-but-present resource means "path not resolved", not "resource not registered".
- **`Domain.Tests` has no runnable host** — its module has no DB provider, so the concrete
  `[Collection]` classes must live in `EntityFrameworkCore.Tests` (Sqlite in-memory).
