# 3.5 — Tesseract OCR into `Attachment.OcrText`

> **Phase:** 3 · **App:** backend · **Commit:** `step(3.5): OCR attachments through an event-enqueued background job` · **Date:** 2026-08-29

## What was built

Stage one of UC-01's AI pipeline, proven **live end to end in this container** (Tesseract, unlike
Ollama, installs fine via apt): upload a PNG through the real API → the `Document` aggregate
queues `AttachmentUploadedEto` → a handler enqueues a one-off job **after the commit** → Hangfire
executes it → Tesseract (`ara+eng`) reads the blob → `OcrText` lands through the aggregate root.
The SQL row now holds `PASSPORT No P-102030 / EXPIRY 2036-03-01` — exactly what 3.6's extractor
will feed the model. No migration: `OcrText` was modeled in Phase 1 *for* this moment. The
enqueue-side and job-side are covered by three pipeline tests on fakes; suites 38 domain + 38 EF
(37 passed, 1 skipped OllamaFact).

## The mental shift

A background pipeline stage has **two halves that fail differently**, and the seam between them
is the commit. Everything before the commit (event, handler) must only *promise* work; everything
after (queue, job) must *assume nothing* — the document may be gone (`FindAsync`, not `GetAsync`),
the work may be done already (`OcrText != null`), the file may be unreadable (null ≠ "", "can't
read" ≠ "read nothing"). Once each half honors its side, the whole pipeline becomes safe to
retry anywhere. The second shift: `ITransientDependency` on the job is not just DI plumbing —
ABP's job discovery hooks *registration*, so a job that isn't registered isn't merely
unresolvable, it silently never runs (found the honest way: a red test).

## Gotchas hit

- `AsyncBackgroundJob<TArgs>` does **not** self-register: two tests failed with Autofac's
  "AttachmentOcrJob has not been registered". The docs' `, ITransientDependency` on the job class
  is load-bearing — it feeds both DI and `AbpBackgroundJobOptions` job discovery.
- Recording fakes as collection-wide singletons made assertions order-dependent (1 red on the
  first full run): fixed by clearing recorders in the test ctor (`AttachmentOcrPipelineTests.cs:43`)
  and scoping asserts to this test's attachment id.
- A ~1-in-14 suite flake turned out to be `SqliteConnection.Close()` NRE-ing during module
  **shutdown** — the driver's close walks its command list while the finalizer thread clears it.
  Isolated the failing test 12×0 to prove it, then hardened teardown
  (`WathiqEntityFrameworkCoreTestModule.cs:87`) — assertions are long past by then.
- A "green" 5×-suite run was on a **stale binary**: the preceding build had 2 errors (missing
  `using System;`) and `--no-build` happily tested yesterday's DLLs. Same trap as the 2.3
  migrator — `grep -c error` on the build output *before* trusting any `--no-build` run.
- `sqlcmd` vanished from the container (restart wiped it); `docker exec wathiq-sql
  /opt/mssql-tools18/bin/sqlcmd` is the resilient spelling. Also the table is
  `documents.Attachment` — ABP's singular table naming, three phases in and it still surprises.

## Check yourself

1. Why must the handler enqueue in `OnCompleted` instead of calling `EnqueueAsync` directly, when
   ABP's *default* job store would actually be transactional?
2. The job found `OcrText != null` and returned without calling the engine. Name the two distinct
   scenarios that make this line necessary.

<details><summary>Answers</summary>

1. Because the abstraction's *Hangfire* implementation enqueues immediately to Hangfire's own
   storage, outside the upload's transaction — the job could execute before the attachment row
   commits, or execute for a row that rolls back. `OnCompleted` re-ties the enqueue to the commit
   the way the default store's same-transaction insert would have.
2. A Hangfire **retry** after the job succeeded but its success report failed, and a **duplicate
   enqueue** (e.g. a future re-upload path or manual requeue from the dashboard). Both re-enter
   `ExecuteAsync`; the state check makes both no-ops instead of double OCR runs.

</details>
