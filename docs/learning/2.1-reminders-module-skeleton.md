## The mental shift

The second module is where the recipe stops being "what the template generated" and becomes
*owned*: every file here was written knowing which executable needs it and why — the factory for
`dotnet ef` (a process with no ABP application at all), the schema migrator for DbMigrator, the
`DependsOn` pairs for host and migrator, the provider `Configure<>` for the host EF module, the
test host deliberately *not* wired yet (nothing to test until 2.3 — and adding it then is a
conscious act, not an omission). The checklist that Phase 1 taught by failure (1.7, 1.8) ran here
in one pass with zero rediscovery, which is the actual evidence of learning.

## Gotchas hit

- The DbMigrator logs `No instantiatable types implementing IEntityTypeConfiguration were found
  while scanning Wathiq.Reminders.EntityFrameworkCore` — a warning, not an error: expected for a
  module with no entities yet, and it disappears in 2.2. Worth recognizing so it isn't
  "fixed" by adding a placeholder configuration.
- `dotnet-ef` wasn't on this machine; `dotnet tool install --global dotnet-ef` (10.0.11) and the
  design-time factory did the rest — `migrations add` never touches the database, so the LocalDB
  connection string in DbMigrator's appsettings is irrelevant at design time.
- Six wiring points, one commit: slnx, host csproj, host `DependsOn`, host EF csproj + provider
  config, DbMigrator csproj + `DependsOn`. Forgetting any one fails *silently* at a different
  time (build, boot, migrate, seed) — the reason the roadmap step text names the graphs
  explicitly.

## Check yourself

1. The `Initial` migration's `Up()` is empty. What two things still get created on first
   migrate, and by which mechanism?
2. Why does the DbMigrator reference `Wathiq.Reminders.Application` already, when the module
   contains no application services?

<details><summary>Answers</summary>

1. The `reminders` schema and `reminders.__EFMigrationsHistory` — created by EF's SQL Server
   migrations-history repository (configured via `MigrationsHistoryTable("__EFMigrationsHistory",
   "reminders")`), not by the migration body.
2. So that when 2.7 adds a `PermissionDefinitionProvider` there, the migrator's graph already
   defines those permissions at seed time — preventing a repeat of the 1.7 bug where admin was
   never granted the Documents permissions because the definitions weren't in the migrator's
   module graph.

</details>
