## What was built

FR-REM-004 across the module boundary without a single cross-module reference:
[DocumentExpiryChangedEto](../../backend/modules/Shared/Wathiq.Shared/Events/DocumentExpiryChangedEto.cs)
lives in `Shared` (null expiry = "stop reminding");
[Document](../../backend/modules/Documents/Wathiq.Documents.Domain/Documents/Document.cs) now
queues it via `AddLocalEvent` from *inside the aggregate* — `SetValidity` publishes only when the
value object actually changed, `MarkRenewed` rides that same path, `Archive` and the app
service's delete publish the stop signal;

chain on SQLite: create → 4 pending rows, renew → the same 4 rows re-armed, delete → all
cancelled; and an update that changes nothing leaves the reminders' `LastModificationTime`
untouched. Suites: 33 + 19, green.

## The mental shift

The event's publisher moved *down* a layer during design. First instinct: publish from
`DocumentAppService` after each save — visible, but forgettable, and Phase 3's extraction
pipeline (which will also touch validity) would have to remember to publish too. Putting
`AddLocalEvent` inside `SetValidity` makes announcing a *consequence of the mutation itself*:
whoever changes the validity, through any future code path, publishes — and the value-object
equality check means the aggregate also decides what "changed" means. The second realization:
ABP local events are **transactional glue, not messaging** — the reminder rows and the document
row commit together, which is exactly right for consistency and exactly why the handler must not
do slow or fallible work like SMTP. The nightly job exists precisely because delivery must NOT
be in this transaction.

## Gotchas hit

- Soft delete never calls an aggregate method — `repository.DeleteAsync` flags the tracked
  entity — so nothing inside `Document` runs at delete time. The stop-event needed an explicit
  `PublishRemindersStop()` call in `DeleteAsync` before the delete; a comment on the method
  records why it is public.
- The renew path almost double-published: `MarkRenewed` originally assigned `Validity` directly
  and would have needed its own event; routing it through `SetValidity` gave it the equality
  gate and one single publish point. Order matters there: `PreviousExpiryDate` must be captured
  *before* `SetValidity` overwrites the value.
- The "unchanged update" test needed a subtle assertion: you can't observe "no event fired"
  directly, so it pins the *effect* — reminders' `LastModificationTime` values are identical
  before and after the notes-only update. Testing absence means finding its observable shadow.

## Check yourself

1. Why does the handler live in the same unit of work as the document save, and what concrete
   design constraint does that impose on 2.6's email channel?
2. A future Phase-3 extraction service sets a document's validity after OCR confirmation. What
   does it have to do so reminders stay correct?

<details><summary>Answers</summary>

1. ABP local events publish inside the publisher's transaction: reminders and document commit or
   roll back together. Consequently the handler must be fast and reliable — actual email sending
   would make document saves fail on SMTP hiccups, so delivery belongs to the nightly job
   (2.5/2.6), not the event handler.
2. Nothing. Calling `Document.SetValidity` (the only way to change validity) queues the event
   automatically, and the equality gate keeps a confirmation that didn't change dates silent.
   That automation is exactly why the event moved into the aggregate.

</details>
