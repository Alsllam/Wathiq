# 4.4 — Auth against ABP OpenIddict

> **Phase:** 4 · **App:** frontend (+backend config) · **Commit:** `step(4.4): wire code+PKCE auth with signal state against OpenIddict` · **Date:** 2026-08-29

## What was built

`libs/shared/auth`: an `AuthService` façade over `angular-oauth2-oidc@20` where the library's
event stream feeds ONE signal and `userName` derives from ID-token claims; `provideWathiqAuth`
(config + an app initializer that consumes the `?code=` return); a functional `authInterceptor`
(bearer on API calls only) and `authGuard`. Backend's share: `Wathiq_App` gets
`http://localhost:4200` as redirect/post-logout (via seeder), `App:CorsOrigins` learns the SPA
origin, and the migrator's content root is pinned so config loads regardless of cwd. **Proven
live in a real browser**: Playwright drove portal → sign-in → OpenIddict login page →
credentials → back with the code → token exchange → "admin" + logout rendered in the ar-first
header. 11 unit tests, lint, build — green across four projects.

## The mental shift

An SPA's auth is a *state machine you don't own* — the library owns redirects, storage and
timers; the app's job is to project that machine into its own state model **once** and consume
it like any other signal. Every place that would have asked `oauthService.hasValidAccessToken()`
imperatively is instead derived from one signal set at one edge — which is why login "just
worked" in the header, guard and interceptor simultaneously the moment the exchange finished.
The debugging session taught the second lesson: **OIDC failures are exact-string failures** —
an issuer differing by one trailing slash, a client invisible because a *soft-delete flag* — the
protocol's cross-checks make "almost right" identical to "wrong", so verification has to read
the server's own words (discovery doc, error codes, the SQL row) rather than eyeball configs.

## Gotchas hit

- **The vanishing config**: `dotnet run` from the repo root gives the migrator a content root
  with no `appsettings.json` — migrations still work (env conn string) while the OpenIddict
  section silently reads empty, so the client seeded with NULL redirect URIs and nobody noticed
  for three phases. Fixed for good with `UseContentRoot(AppContext.BaseDirectory)`
  (`Program.cs:37`); diagnosed only after a decompile detour wrongly blamed ABP's update path.
- **My "fix" made it worse**: a self-healing delete-and-recreate in the seeder soft-deleted the
  app (`OpenIddictApplication` is ISoftDelete!) — raw SQL `COUNT(*)` said one healthy row while
  the host's filtered queries saw none (`ID2052: client_id invalid`). The EF command log's
  `[IsDeleted]` column cracked it. Restored the flag, deleted the "fix": the update path was
  never broken, only its input.
- `invalid issuer ... expected: https://localhost:44352 current: https://localhost:44352/` —
  OpenIddict's issuer has a trailing slash; the config must match byte-for-byte.
- The dev login page **autofills the demo credentials after load**: Playwright's `fill` ran
  first, the page's script appended, and `admin` became `adminadmin` — "Invalid username or
  password!" with correct credentials in the script. A settle-wait + fill + assert-before-submit
  fixed it; curl replaying the form (302) was what proved the server side innocent.
- `angular-oauth2-oidc@latest` peer-depends on Angular 22 — pin the major to the framework
  (`@20`). And the lib generator, run while `package.json` was mid-broken, failed *silently
  partway* (src there, no project.json, no tsconfig path) — a generator's short output is worth
  reading as a failure report.

## Check yourself

1. Why does the bearer token attach in an interceptor rather than the API client lib adding a
   header parameter to each call?
2. The host said `client_id is invalid` while `SELECT COUNT(*)` found the row. Reconstruct the
   mechanism and name the general lesson about "checking the database".

<details><summary>Answers</summary>

1. Cross-cutting once vs remembered-everywhere: the interceptor sees every HttpClient request,
   applies the token to API-bound URLs only, and auth stays invisible to feature code — the
   same argument as ABP's audit/tenant middleware living in the pipeline, not in services.
2. ABP's OpenIddict entities are soft-delete; repository/host queries carry the `IsDeleted = 0`
   filter while raw SQL does not. The row existed *and* was invisible - both observations true.
   Lesson: when app and SQL disagree, suspect the query filters (soft delete, tenant) before
   suspecting either side of lying; SELECT the filter columns explicitly.

</details>
