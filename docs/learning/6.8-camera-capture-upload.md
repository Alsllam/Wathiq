# 6.8 — Camera capture → create + upload

> **Phase:** 6 · **App:** mobile · **Commit:** `step(6.8): capture a document photo and create-with-upload through a faked-at-the-wall camera` · **Date:** 2026-09-07

## What was built

UC-01's write side: a FAB on the documents tab opens `/documents/new` (the literal route
declared BEFORE `:id` — 5.7's route-order lesson, third stack), a form with type chips, an
LTR number field, a date picker, and capture/gallery buttons. The camera hides behind an
`ImageCapture` wall (own `CaptureSource` enum, `CapturedImage` as *bytes* — trivially fakeable,
and the upload wants bytes anyway; capped at 2400px/q85 because OCR needs legibility, not a
12MP upload). The whole submit lives behind `createDocumentSenderProvider`: resolve the self
holder (FR-DOC-007), POST create (null-aware elements — `'number': ?draft.number` — keys vanish
with their nulls), multipart upload with field name `file` *from the swagger contract*, then
invalidate the list and hand back the id for `pushReplacement` to the detail. iOS
`Info.plist` gained the camera/photos usage strings — bilingual, stating the privacy promise.
A failed save keeps the form and its data: retry is free. `flutter analyze` 0 issues, 28 tests
green.

## The one new concept

**Platform permissions and plugin-backed IO.** The camera never belongs to the app:
`image_picker` hands the request to the OS (an intent on Android, the system picker on iOS),
*the user* grants access in system UI, and the app receives exactly one blessed file — it never
browses the camera roll. The two build-time truths that come with that: iOS **crashes on first
use** without `NSCameraUsageDescription`/`NSPhotoLibraryUsageDescription` in `Info.plist`
(permissions are declared in native manifests, not requested in Dart), and the plugin being a
platform channel means the honest test boundary is the wall — inject bytes where the channel
would be, and everything beneath (preview, draft assembly, submit, redirect) is real code under
test.

## The mental shift

The bug that mattered was invisible until the *second* test ran: the `GoRouter` was a global
`final`, and **a router is navigation state, not configuration** — test 1 parked it on the new
document's detail, and test 2's freshly pumped app woke up there, FAB nowhere in sight. Moving
it into a `Provider` made each `ProviderScope` a genuinely fresh world and — the compounding
kind of fix — put the router where auth-based redirects can reach it later. The broader lesson
joins 6.4's: *everything stateful belongs in the container*, and "it's just config" deserves
suspicion whenever the object has a current-location, a cache, or a connection inside it. The
second shift: reading `'file'` out of the captured swagger before writing the multipart call
felt pedantic for one field name — but that field name is exactly the kind of bug that would
survive every container test and surface only on a phone against the real API.

## Gotchas hit

- **`intl` ships its own `TextDirection`** that shadows Flutter's - `textDirection:
  TextDirection.ltr` on the number field failed to compile until the import became
  `import 'package:intl/intl.dart' hide TextDirection;`. A classic, apparently; now it's ours.
- **The global-router test leak** (above): the failure mode was "finder found 0 widgets" two
  tests in, with test 1 green - state leakage across tests smells exactly like this, and the
  3.5 order-dependence lesson translated straight into Flutter.
- The analyzer's `use_null_aware_elements` upgraded my `if-case` map entries to `?value`
  syntax I hadn't met yet - strict lints as a Dart tutor again.

## Check yourself

1. Why does `CapturedImage` carry bytes instead of a file path, when a path would be cheaper?
2. The FAB opens `/documents/new`, declared before `/documents/:id`. What happens if the order
   flips, and when would you find out?

<details><summary>Answers</summary>

1. Three reasons converge: the upload API wants bytes (a path would be read anyway); a path
   couples consumers to a filesystem that widget tests don't have (bytes are fakeable with
   `Uint8List.fromList`); and the picker's temp file lifetime is platform-owned - bytes copied
   once are safe, a path can dangle. When 6.10's offline queue arrives, bytes also serialize
   into Drift directly.
2. `:id` would match first and 'new' becomes a document id: the detail page requests
   `/api/documents/documents/new`, which 400s/404s - at RUNTIME, on navigation, with a
   confusing error screen. The container flow test catches it here (the form never appears),
   which is exactly why the route-order comment cites 5.7: the same landmine exists in every
   router that matches top-down.

</details>
