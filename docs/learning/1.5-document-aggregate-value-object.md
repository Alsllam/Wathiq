## The mental shift

The 1.CP question answers itself once you try to write the rule as a nullable `DateTime`:
"expiry ≥ issue" needs *both* dates, so it cannot live on either property's setter — it would
have to be re-checked in every service that touches either one. Making the pair a value object
moves the rule to the single place the pair is created. The database still sees two `date`
columns; only the code gained a type. The same logic put `Attachment` inside the aggregate: its
lifecycle rule ("no attachment without a document, delete the blob after removing") belongs to
`Document`, not to a repository.

## Gotchas hit

- **ABP `ValueObject` does not override `Equals`.** `a.ShouldBe(b)` failed for two equal periods
  and the persistence round-trip test failed the same way. Added `Equals`/`GetHashCode` delegating
  to `ValueEquals`/the atomic values.
- `EntityNotFoundException` lives in `Volo.Abp.Domain.Entities`, not `…Entities.Auditing` — one
  more explicit `using` (no `ImplicitUsings` in this template, as noted in 1.2).
- `sqlcmd` string concatenation across `sys.*` columns hit a collation conflict; select the
  columns separately instead of building one string.
- The `IX_Document_OwnerUserId_ExpiryDate` composite from `database.md` cannot be declared on the
  owned property from the root builder in one call; I indexed `ExpiryDate` inside `OwnsOne` and
  `OwnerUserId` separately, and noted the composite as deferred to 1.6 when the timeline query exists.

## Check yourself

1. Why is `ExpiryDate` not a nullable `DateTime` property on `Document` with validation in the setter?
2. How does an `Attachment` get deleted, and who deletes the file bytes?

<details><summary>Answers</summary>

1. The rule compares expiry with issue, so it belongs to the pair; a value object (`ValidityPeriod`)
   validates once in its constructor, is immutable and compared by value, and EF's owned-type
   mapping keeps the two `date` columns unchanged.
2. Only through the root: `Document.RemoveAttachment(id)` removes the child (EF cascades the row)
   and returns the `BlobKey`; the application service (step 1.6) deletes the file via `IFileStore`
   after the unit of work commits, so a rolled-back transaction never loses a file.

</details>
