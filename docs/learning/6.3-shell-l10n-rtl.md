# 6.3 — App shell: theme + ar/en + RTL

> **Phase:** 6 · **App:** mobile · **Commit:** `step(6.3): add the localized RTL app shell with theme and bottom navigation` · **Date:** 2026-09-07

## What was built

The placeholder gave way to the real shell: `MaterialApp` wired with `flutter_localizations`,
ARB files where **Arabic is the template** (`l10n.yaml`: a key missing in en falls back to ar,
never the reverse), a language toggle in the AppBar, Material 3 theme seeded from the portal's
emerald (`0xFF059669` — two apps, one product), and a three-tab `NavigationBar` scaffold whose
tabs hold "built in step X" placeholders until 6.4/6.7/6.9 land. RTL required **zero manual
work**: the `ar` locale installs `Directionality.rtl` for the whole tree, and the test asserts
exactly that — `Directionality.of(context)` flips with the toggle. `flutter analyze` 0 issues,
10 tests green (3 new shell tests), in-container.

## The one new concept

**`BuildContext` — where "inherited" things come from.** Angular delivers locale, theme and DI
through providers configured at bootstrap; Flutter delivers them as *widgets above you in the
tree*, and `context` is your position in it. `AppLocalizations.of(context)`,
`Theme.of(context)`, `Directionality.of(context)` all do the same thing: walk up to the nearest
ancestor that installed that value (`MaterialApp` installs all three at the root). That's why
localizing the app is one `locale:` property, why theming is one `theme:` property, and why the
AppBar's `actions` land on the correct side in RTL without any `ms-`/`me-` discipline — the
framework's equivalent of logical CSS properties is simply *the tree*.

## The mental shift

The portal's RTL correctness was a *discipline* — logical properties only, reviewed in every
diff since 4.2. Here it's a *property of the platform*: the moment the locale is `ar`, the
entire tree lays out RTL, and the temptation to "check the mirroring" dissolves into one test
line asserting `Directionality.of`. That reframed what the shell test should even say: not
"the toggle button sits on the left" (an implementation detail the framework owns) but "text
AND direction flip together" (the user-visible contract). The second shift: generated
localizations are *typed methods*, not string keys — `l10n.comingSoonStep('6.4')` with a typed
placeholder means a missing key or wrong-arity call is a compile error, which is Transloco's
missing-key runtime warning promoted to edit time, the same promotion null safety made in 6.2.

## Gotchas hit

- **The unasserted `.replace` bit twice in one step**: both pubspec patches printed success
  while silently no-opping (the real file had comments between my anchor lines), surfacing
  later as `uri_does_not_exist` for a package that was "added". The 5.x patch discipline -
  `assert old in s` before every replace - exists precisely for this; skipping it because
  "it's just pubspec" cost two debug loops.
- **`synthetic-package: false` is now deprecated noise**: Flutter 3.41's gen-l10n warns it has
  no effect (non-synthetic output became the default). Removed; `output-dir: lib/l10n/gen`
  keeps the generated files visible and committed.
- `flutter gen-l10n` refuses to run without `flutter: generate: true` in pubspec even when
  `l10n.yaml` is complete - the flag and the config file are BOTH required, and only the error
  message for the missing flag mentions the other half.

## Check yourself

1. Trace what happens, mechanically, when the toggle switches ar→en: which widget rebuilds,
   and how do descendants find out?
2. Why does the ARB approach make "Arabic-first" stronger than the portal's Transloco setup?

<details><summary>Answers</summary>

1. `setState` in `_WathiqAppState` marks that State's subtree dirty; `build` runs again and
   MaterialApp receives `locale: en`. MaterialApp installs new Localizations and Directionality
   widgets; every descendant that looked things up via `.of(context)` registered a dependency
   on those inherited widgets, so exactly those descendants rebuild - text re-resolves to en
   and layout flips ltr in the same frame. Nothing subscribes, nothing injects: the tree IS
   the dependency graph.
2. Transloco falls back at RUNTIME (missing en key → ar string appears, logged as a warning).
   gen-l10n generates the API from the Arabic template at BUILD time: en missing a key still
   compiles (falls back to ar), but a key absent from ar - the template - doesn't exist as a
   method at all, so no screen can ship referencing a string that has no Arabic. The product
   rule became unrepresentable-as-wrong.

</details>
