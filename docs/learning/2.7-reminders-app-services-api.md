## The mental shift

`PUT /rule` is not a row update — it's a **command with derived consequences**, and deciding
where the consequences live was the real work. The naive version updates the rule and lets the
nightly job "figure it out"; but the job only dispatches, it never re-plans. The honest contract
is transactional: settings and the schedule they imply change together, or not at all — which is
why `ResyncForUserAsync` runs inside the update's UoW, and why the test asserts the upcoming
list *immediately* after the PUT. The enabler was a 2.3 design decision made for other reasons:
because a reminder row carries `DueDate + OffsetDays`, the schedule is reconstructible from the
Reminders module's own data — the boundary held without an event round-trip to Documents.

## Gotchas hit

- Assumed the route would be `…/upcoming`; the convention derived `…/upcoming-list` from
  `GetUpcomingListAsync` — the first live call went to my guess and returned nothing. 1.7's
  lesson re-learned in miniature: the spec is the artifact, read it before curling.
- The bad-time-zone test relies on UoW rollback, not on the entity's own ordering: `SetOffsets`
  has already mutated the tracked rule when `SetTimeZone` throws, and only the aborted unit of
  work makes "changes nothing" true. Worth knowing which mechanism is actually doing the work.
- The resync interplay with history: after PUT `[45,3]`, the 45-day due date was already past
  (dropped by `ComputeSchedule`), the Sent 7-day row was *not* in the desired set → `Cancel()`
  correctly refused to touch it (Sent is final), the 1-day row went Cancelled. The live upcoming
  list showing exactly one row was the sum of four earlier design decisions behaving together.

## Check yourself

1. Why do the rule's routes have no `{id}`, and what selects the row instead?
2. Changing offsets must reshape existing reminders, yet Reminders never queries Documents for
   expiry dates. Where does the expiry come from?

<details><summary>Answers</summary>

1. One rule per user (database-unique `UserId`): the resource is a singleton per caller, so
   `CurrentUser` — carried by the bearer token — selects the row; an `{id}` would only invite
   passing someone else's.
2. From the module's own rows: any reminder's `DueDate + OffsetDays` reconstructs the document's
   expiry (max across the group guards stale cancelled rows), so `ResyncForUserAsync` re-derives
   and re-syncs per document without crossing the module boundary.

</details>
