## The mental shift

Tooling files are **contracts, not chores**: `.gitattributes` decides what a diff means,
`.editorconfig` decides what "formatted" means for three languages, and the Compose healthcheck
decides what "the database is up" means for the API that will depend on it. Getting them into the
repo before any code means every later step inherits them instead of retrofitting.

## Gotchas hit

- `.env.example` was silently ignored by the existing `.env.*` rule; added `!.env.example`.
  Lesson: after adding a "committed example" file, `git status` it explicitly.
- `git add --renormalize .` after adding `.gitattributes` changed nothing — the repo was already
  LF because `core.autocrlf=true` converted on commit; the warnings were about the working copy.
- The MSSQL image's `sqlcmd` lives at `/opt/mssql-tools18/bin` and needs `-C` (trust cert); the
  older `/opt/mssql-tools` path in most tutorials no longer exists in the 2022 image.
- `$$` in Compose escapes `$` so the container shell, not Compose, expands `MSSQL_SA_PASSWORD`.

## Check yourself

1. Why is `*.ps1` forced to CRLF while everything else is LF?
2. What happens if you run `docker compose up` without a `.env`?

<details><summary>Answers</summary>

1. PowerShell/cmd on Windows can misparse LF-only scripts (especially here-strings and
   `--%`); `.gitattributes` keeps them CRLF regardless of `core.autocrlf`.
2. Compose aborts with "set SQL_SA_PASSWORD in .env" because of the `${VAR:?msg}` syntax —
   no container starts with an empty SA password.

</details>
