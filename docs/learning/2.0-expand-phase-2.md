## The mental shift

The riskiest thing in this phase is not Hangfire — it's *when idempotency is designed*. Written
as one paragraph, "nightly job + reminders" invites building the job first and discovering
duplicate sends later. The expansion forces the invariant to exist as schema (2.3's unique index
and status enum) and as pure, clock-free date math with tests, before any job scheduler or SMTP
appears. By the time 2.5 arrives, "safe to run twice" is a property the job *inherits* from the
data model, not a feature bolted onto it — which is exactly the 2.CP checkpoint answer.

2. The nightly job (2.5) comes before the email channel (2.6). What can 2.5's "send" do without

<details><summary>Answers</summary>

1. Both modules must see the type but neither may reference the other (no cross-module project
   references); `Shared` is the only module everyone may depend on, so cross-module contracts —
   like cross-cutting services — live there.
2. 2.5 claims the reminder (status transition under the unique index) and hands it to a channel
   abstraction; with no channel yet it can only log/mark. That proves idempotent claiming in
   isolation, so 2.6's SMTP failures can't be confused with scheduling bugs.
