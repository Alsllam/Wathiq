## What was built

The fifth module, from memory: four projects under `backend/modules/Guides/`, a `GuidesDbContext`
pinned to schema `guides` with its own `guides.__EFMigrationsHistory`, an **empty** `Initial`
migration, and registration in **all three executable graphs** (host, DbMigrator, SQLite test
host) plus `Wathiq.slnx` — one commit, exactly the settled recipe. The one new design decision:
`GuidesPermissions` defines a **single grantable name**, `WathiqGuides.Manage` (authoring,
admin-only); reading guides is deliberately permissionless because published renewal guides are
public content. Verified live: migrator run put `20260903113549_Initial` into
`guides.__EFMigrationsHistory` and `WathiqGuides.Manage → R/admin` into `AbpPermissionGrants`;
all three suites green (41 + 18 + 49-with-2-gated-skips).

## The mental shift

Writing the same module the fifth time surfaced what the recipe is actually *for*: the value was
never the files (they're near-identical), it is the **checklist of composition points** — host
DependsOn ×2, host csproj ×2, host-EF per-context config, migrator DependsOn ×2, migrator csproj
×2, test DependsOn, test csproj, test per-context config, test CreateTables, slnx. Ten wiring
edits for fourteen new files, and every past module's bug in this area was a missed wiring edit,
never a wrong file. The permission decision was the real thinking: Documents taught "define a
name per operation"; Guides teaches the opposite discipline — *don't* define names for access you
intend to be universal, because every defined name is a grant someone can forget, and a public
service whose content needs a permission row is broken in its default state.

## Gotchas hit

- An empty migration's `Up()` contains no `EnsureSchema` — I expected to need one by hand, but
  EF's SQL Server history repository creates the `guides` schema itself when placing
  `__EFMigrationsHistory` there; verified in SQL rather than assumed (the row exists, the
  schema exists).
- The migrator csproj needs the **Application** project too, not just EntityFrameworkCore — the
  permission definition provider lives in Application, and without it `WathiqGuides.Manage`
  would never reach `AbpPermissionGrants`. Checked the grant with a real `SELECT`: one row,
  `ProviderName=R`, `ProviderKey=admin`.
- `CreateTables()` for a context with zero entities is a no-op — the block is in the test module
  anyway, commented as ritual: adding it in 5.2 *after* tests start dying with "no such table"
  is the expensive order.

## Check yourself

1. Why does `GuidesPermissions` define exactly one permission when Documents defined nine?
2. The migrator references `Wathiq.Guides.Application` even though 5.1 ships no app services.
   What breaks without that reference, and how would you notice?

<details><summary>Answers</summary>

1. Reading guides is public by design - a permission name for it would be a grant that can be
   forgotten, making the public product broken-by-default. Only authoring needs guarding, and
   one `Manage` name covers it; children can split out later without any migration because
   permissions are definitions, not schema.
2. The permission definition provider lives in the Application assembly. Without the reference
   (and its module in DependsOn) the migrator's seed pass never sees the definition, so
   `WathiqGuides.Manage` is never granted to the admin role - nothing errors, admins just get
   403 on authoring endpoints in 5.2. You notice by SELECTing `AbpPermissionGrants` after the
   migrator run, which is exactly what this step did.

</details>
