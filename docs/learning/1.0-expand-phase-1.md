## The mental shift

A phase description written as one paragraph hides its riskiest decision — here, that
`ExpiryDate` needs to exist as a real value object with EF Core owned-type mapping *before* any
CRUD or API work, because everything downstream (validation, the 1.CP checkpoint question, later
reminder math) depends on it being modeled correctly from the start. Slicing by module layer
(skeleton → entities → services → API → tests) makes that dependency explicit instead of letting
"build the Documents module" hide it.

## Check yourself

1. Why does step 1.5 (the `Document` aggregate) come after 1.4 (`DocumentType`/`Holder`) instead
   of together in one step?
2. Which step is the first one that produces runnable application code, and what does it
   deliberately *not* include yet?

<details><summary>Answers</summary>

1. `Document` has foreign keys to both `DocumentType` and `Holder`; splitting them keeps each
   commit's migration reviewable (CLAUDE.md rule 5) instead of one large migration mixing three
   entities and a value object.
2. Step 1.1 (scaffold the ABP solution) — it deliberately excludes any custom module; it only
   proves Identity and the host boot against LocalDB, so failures there are isolated from the
   `Documents` module work that follows.

</details>
