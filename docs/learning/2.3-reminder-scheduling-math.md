## The mental shift

Idempotency was designed here, two steps before the job that needs it — and it turned out to be
a *data-model property*, not a job property. Because `(DocumentId, OffsetDays)` is unique,
`SyncForDocumentAsync` physically cannot express "insert a second 30-day reminder"; it has to
find and re-arm the existing row. That inverts the usual instinct (write the job, then bolt on
duplicate-protection): by the time Hangfire arrives in 2.5, "safe to run twice" is already
enforced by the schema and proven by a test that runs the same sync twice and counts four rows.
The other shift: `DueDate >= today` needed a *whose-today* answer before it could be written,
which is why `TodayIn(timeZoneId, utcNow)` exists and why the clock had to be pinned to UTC
first — a date comparison is only meaningful after you decide whose calendar it happens on.

## Gotchas hit

- **The 1.3 stale-binary gotcha, repeated:** ran DbMigrator with `--no-build` right after
  `dotnet-ef migrations add` — it reported "successfully completed" while applying *nothing*,
  because the new migration existed as source but not in the compiled assembly. Caught by
  verifying in SQL (0 indexes found) instead of trusting the log line; re-ran without
  `--no-build`. Lesson upgraded: after `migrations add`, the words `--no-build` are banned.
- ABP's `IClock` defaults to `DateTimeKind.Local` — silently fine on a UTC server, wrong
  everywhere else. `TodayIn` also re-asserts `DateTime.SpecifyKind(..., Utc)` defensively, since
  `ConvertTimeFromUtc` throws on a `Local`-kind input.
- The migration timestamp crossed midnight UTC (`202608**28**051505` after yesterday's
  `202608**27**…`) — a small live demonstration of why "today" handling matters.
- The test host would have picked SQL Server for `RemindersDbContext` (the host EF module's
  per-context `UseSqlServer` survives into the test graph) — the SQLite override + `CreateTables`
  in the test module is mandatory, not cosmetic; 1.3's comment about per-context config replacing
  the global default said exactly this.

## Check yourself

1. A user renews a passport, so its expiry jumps five years. Walk through what
   `SyncForDocumentAsync` does to the four existing reminder rows, and why no insert happens.
2. Why is `ComputeSchedule` static, and what does that buy the tests concretely?

<details><summary>Answers</summary>

1. Each row's offset is still in the desired set, but its `DueDate` differs → `Reschedule(new)`
   re-arms the same row (status back to Pending, `SentAt` cleared, delivery history kept). The
   unique index on `(DocumentId, OffsetDays)` means an insert for the same pair would throw —
   reuse is the only legal move.
2. It takes values and returns values — no repository, no clock, no DI. The nine math tests run
   in milliseconds as plain xUnit facts; "time" is just a `DateOnly` argument, so edge cases
   (due today, year boundary, Riyadh midnight) are one-liners instead of mock setups.

</details>
