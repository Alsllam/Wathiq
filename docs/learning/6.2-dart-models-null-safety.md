# 6.2 — Dart models + JSON round-trips

> **Phase:** 6 · **App:** mobile · **Commit:** `step(6.2): add Dart models with manual JSON decoding for guides, chat, documents and reminders` · **Date:** 2026-09-07

## What was built

`lib/core/models/`: the wire types the app will consume, written by hand — `ListResult<T>`
(ABP's envelope, decoded generically via a passed-in item decoder), `GuideSummary` /
`GuideVersion` / `GuideDetail`, the chat contract with its trust fields, `DocumentModel` +
`DocumentType` with enhanced enums mapping the wire's tinyints, and `Reminder`. No codegen on
purpose: the step's job is *reading Dart*, and a hand-written `fromJson` under `strict-casts`
makes every assumption about the wire explicit. Tests decode **payloads captured from the real
API during Phase 5's live laps** — the 5.2 Arabic guide detail and the 5.5 refusal verbatim —
plus swagger-mirrored document/reminder shapes. `flutter analyze` 0 issues, 8 tests green,
in-container.

## The one new concept

**Sound null safety.** `String?` is a *different type* from `String`, not an annotation: the
compiler refuses `fees.length` until flow analysis narrows it, and there is no warning-only
mode to drift through (the C# NRT contrast). The discipline lands at the JSON boundary:
`as String` says "the API always sends this — fail HERE if not", `as String?` says "absence is
data", and once decoded, nothing downstream ever null-checks a non-nullable field. The bonus
teachings that rode along: `required` named parameters (construction sites read like the JSON),
factory constructors, and enhanced enums with fields (`DocumentStatus.fromWire`) replacing
scattered magic ints.

## The mental shift

Writing `fromJson` by hand felt like a step backwards from openapi-typescript — until the
analyzer started doing the portal's *runtime* work at *edit time*. In the portal, optionality
lives in generated types and bites during AOT builds or live clicks; here, deciding `String`
vs `String?` per field forced reading the API contract closely enough to notice things codegen
had hidden (every document field except ids and status is optional — 6.7's screens now MUST
design their empty states, the compiler will not let them forget). Manual mapping is not the
long-term answer — `json_serializable` exists and later steps may adopt it — but as a first
Dart exercise it turned "boilerplate" into a guided tour of exactly the features (factories,
named params, flow analysis, first-class functions) the rest of the phase builds on.

## Gotchas hit

- **`DateTime.parse` accepts the date-only string** (`"2026-09-01"` → midnight, no timezone) -
  no `DateOnly` twin exists in Dart core; fine for display, and worth remembering when 6.9
  compares dates across timezones.
- **`strict-inference` rejects `jsonDecode(...)` used raw**: its static type is `dynamic`, so
  every call site casts `as Map<String, dynamic>` - annoying for exactly one line per test,
  and precisely the point of having turned the flag on.
- The chat response's real invariant ("`answer` is null exactly when `answered` is false")
  is inexpressible on a plain class - no discriminated unions here (sealed classes could model
  it; deferred until the concept budget allows). The contract comment + the refusal test carry
  it for now.

## Check yourself

1. Why does `DocumentModel` make `expiryDate` nullable while `Reminder` makes `dueDate`
   non-nullable, when both come from the same backend?
2. What breaks, and where, if the backend renames `titleAr` to `titleArabic`?

<details><summary>Answers</summary>

1. Because the WIRE differs: FR-DOC-002 lets users store documents without dates, so the API
   can send null - the model must carry that as `DateTime?` and every screen must handle it.
   A Reminder row cannot exist without a due date (the scheduler computes it), so the API
   always sends one - `DateTime` (non-null) encodes that guarantee and spares all downstream
   null checks.
2. `json['titleAr'] as String` casts null to String and throws at DECODE time - the captured-
   payload test fails first (if the fixture is refreshed) or the screen's fromJson throws with
   a clear cast error naming the line. Sound null safety turns a silent undefined-in-the-UI
   into a loud boundary failure.

</details>
