# 4.2 — i18n + RTL foundation (`shared/i18n`)

> **Phase:** 4 · **App:** frontend · **Commit:** `step(4.2): add the ar-first i18n lib with a language signal driving direction` · **Date:** 2026-08-29

## What was built

The first Nx lib, `libs/shared/i18n` (`scope:shared` — the 4.1 boundary rules' first subject):
Transloco 8 (`@jsverse`) with **Arabic as the default**, a `LanguageService` where one `lang`
signal is the source of truth and direction/locale/`<html>` attributes/Transloco's active lang
all *derive* from it, registered ar+en locale data, an Arabic-capable system font stack via
Tailwind's `@theme`, and the shell converted to translation keys with a working toggle. Proven:
5 unit tests green (lib 3 + app 2, including "toggle flips the rendered language *and* `dir`"),
lint + build green, and a live serve confirmed `/i18n/ar.json` served and `dir="rtl"` rendered.

## The mental shift

`dir` is state, and almost nothing else about RTL is. Every previous RTL project I've seen keeps
direction alive in three places — a service field, CSS overrides, template conditions — and they
drift. Here the whole mechanism is: one signal, one `computed`, one `effect` writing two
attributes, and a class vocabulary (`ms-`/`me-`/`text-start`) that never mentions a side. The
toggle test is the proof of the architecture, not just of the feature: it asserts the *rendered
text* and the *document direction* moved together because they cannot move apart. And the
`effect` here is the checkpoint's "rare legitimate one" — it doesn't derive state (computed
does that), it synchronizes state out of Angular's world.

## Gotchas hit

- Jest, twice, same disease: `@jsverse/utils` then `@angular/common/locales/ar` — ESM syntax in
  `.js` files that the default `transformIgnorePatterns` (`.mjs` only) refuses to transform.
  Each surfaced as "Unexpected token 'export'" pointing INSIDE node_modules.
- JSON imports under Jest's CJS interop arrive as `{default: {...}}` — Transloco flattened that
  into `default.shell.appName` keys and the pipe rendered raw key names. `require()` in the spec
  returns the naked object.
- `reRenderOnLangChange` defaults to **false**: the toggle test failed with the click "working"
  (service flipped, `dir` flipped) while the pipe stayed Arabic — the testing module's config
  must repeat production's `true` or the test exercises a different i18n behavior than users get
  (`app.spec.ts:25`).
- The generator scaffolds every new lib zone-ful (`setupZoneTestEnv`) in a workspace with no
  zone.js — the lib's `test-setup.ts` needs the zoneless swap every time; worth remembering for
  4.3's lib.

## Check yourself

1. Why is `dir` a `computed` and the DOM write an `effect`, rather than `toggle()` setting all
   three (signal, attribute, storage) imperatively?
2. The toggle test passed `whenStable` but showed Arabic before the `reRenderOnLangChange` fix —
   what exactly was and wasn't updating, and why did the test catch what a quick manual check
   might not?

<details><summary>Answers</summary>

1. Imperative fan-out is three writes that must never be forgotten anywhere else `lang` might
   change (a future login-profile load, a deep link). With derivation + one edge effect, any
   writer of the one signal gets the full fan-out for free — the same reason `SetValidity`
   publishes its own event instead of trusting every caller to.
2. The service and `dir` updated (signals worked); only Transloco's rendered output was frozen,
   because the pipe re-renders on lang change only when configured to. A manual check that only
   eyeballed layout mirroring would pass; the test asserts text AND direction together, pinning
   the pair that must move as one.

</details>
